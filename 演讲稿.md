## Slide 4 — Problem（问题背景）约 60 秒

The connected environments theme asks us to think about how the physical world around us shapes our digital experience — and vice versa.

For urban runners, this question is very real.

When I go for a run in London, I have four questions that no standard fitness app answers:
- Is the **air quality** safe enough to run in right now?
- Is the **temperature and humidity** comfortable?
- Can I see exactly **where I ran** on a map?
- And am I running at a **cadence** that's actually efficient?

These questions connect the physical environment to the physical activity. 

Air quality in particular is something most people ignore — but AQI above 150 causes measurable respiratory stress during aerobic exercise. For an urban runner, this matters every single day.

Urban FitLog was built to answer all four of these questions, in real time, in one app.

## Slide 5 — App Overview（应用概览）约 45 秒

The app is structured around four modules.

**Strength Training** — this handles gym-style workouts. You can log exercises from a database of over 50 movements, track sets, weight, and reps, use workout templates, and calculate calorie burn.

**Aerobic Running** — this is the core Connected Environments feature. It combines live GPS tracking on an OpenStreetMap map, real-time air quality from AQICN, weather data from OpenWeatherMap, and cadence sensing from the accelerometer — all running simultaneously.

**Activity Calendar** — every run and training session is logged and visible in a monthly calendar view, with badges per day.

And **Settings** — where you configure body data for calorie calculations, enter your API keys, switch language, and toggle between light and dark mode.

## Slide 7 — Sensors（传感器）约 60 秒

Let me start with the onboard sensors, because this is what makes the app "connected" at the hardware level.

I used **three sensors** from the phone itself.

First, **GPS** via the `geolocator` package. This gives me a continuous position stream, which I use to draw the route polyline, calculate distance using the Haversine formula, and derive pace.

Second, the **accelerometer** via `sensors_plus`. Raw accelerometer data gives me the magnitude of movement — I compute √(x² + y² + z²) on each sample, detect peaks in that signal, and count peaks per unit time to derive **cadence in steps per minute**. This is the same principle used in commercial running watches.

Third, the **pedometer**, which gives me cumulative step count using the phone's built-in motion coprocessor — more accurate than my accelerometer peak detection for total steps.

Together, these three sensors give me a full picture of the runner's physical performance, entirely from the phone's built-in hardware.

## Slide 8 — Cloud APIs（云端 API）约 50 秒

On top of the onboard sensors, I integrated three external cloud APIs to bring in environmental data.

**OpenWeatherMap** gives me temperature, humidity, wind speed, and weather description, fetched based on the user's GPS coordinates.

**AQICN** gives me the real-time Air Quality Index — a value from 0 to 500, categorised as Good, Moderate, Unhealthy, or Very Unhealthy. The app shows this before a run so the user can decide whether it's safe to go out.

And **CARTO tiles** via `flutter_map` provide the OpenStreetMap base map.

The data flow is: GPS location → HTTP request → JSON parse → UI render. This happens automatically when the user opens the Running tab, and updates continuously during a run.

## Slide 10 — Key Technical Decisions（关键技术决策）约 75 秒

I want to walk you through four engineering decisions that had the biggest impact on making this app work reliably.

**First: the `_runActive` flag.**
When the user presses Pause or Stop, the naive approach is to cancel the GPS stream and the accelerometer stream in the button handler. On iOS, this causes the main thread to freeze — the UI becomes completely unresponsive for several seconds.
My solution: never cancel native streams in button handlers. Instead, all three streams run continuously, and their callbacks simply check the `_runActive` flag and return immediately if it's false. The streams are only cancelled in `dispose()`, which is the correct iOS lifecycle point.

**Second: `IndexedStack` for the map.**
Instead of switching between an idle view and a running view using a conditional widget, I wrap them in an `IndexedStack`. This keeps the `FlutterMap` widget alive in the widget tree even when the idle view is shown. Without this, every state transition destroys and recreates the map, triggering an NSURLSession crash on iOS.

**Third: CARTO tiles and the ATS exception.**
The default OpenStreetMap tile server serves tiles over HTTP, which iOS blocks by default under App Transport Security. And OSM tiles were also throttled on the device. I switched to CARTO Voyager tiles — served over HTTPS across four subdomains — and added `NSAllowsArbitraryLoads` to the Info.plist. After that, the map loaded instantly.

**Fourth: `getCurrentPosition()` plus `distanceFilter: 0`.**
GPS streams have a cold-start delay of 5–10 seconds. If you only subscribe to the stream, the map is blank when the run starts. I pair a one-shot `getCurrentPosition()` call with the stream subscription, so the map centres on the user immediately.

These four decisions together are what made the difference between an app that freezes and one that runs smoothly.

## Slide 12 — Strength Training & Calendar（力量训练与日历）约 45 秒

Beyond the running feature, the app includes a full **strength training logger**.

You can browse over 50 exercises organised by muscle group — all bilingual in Chinese and English. For each exercise, you log sets, weight, and reps. There's a rest timer with an animated clock face, support for workout templates, and calorie calculation using the MET formula — MET × body weight × duration.

The **Activity Calendar** brings everything together. Every day you've trained shows a badge — green for a strength session, and a distance badge for any runs. Tapping a day opens a detail sheet showing the full workout log and run history for that day.

This gives users a long-term view of their training habits alongside their environmental context.

## Slide 13 — Challenges & Reflection（挑战与反思）约 50 秒

Let me be honest about what was hard.

The **iOS thread freeze** was the most unexpected problem. I didn't know that cancelling a native EventChannel subscription on the main thread could block the UI entirely. Understanding *why* this happens — and finding the `_runActive` flag pattern as the solution — taught me a lot about how Flutter interacts with native iOS APIs.

The **map tiles not loading** cost me significant time. I had a working map in the simulator but blank grey tiles on the device. The root cause turned out to be two separate issues: iOS ATS blocking HTTP, and OSM tiles being rate-limited. Solving it required switching tile providers and modifying the app's transport security settings.

The **GPS cold start delay** was a UX problem I didn't anticipate — the map just showed nothing for the first ten seconds of a run, which felt broken.

And finally, putting 5,100 lines in a single `main.dart` was a pragmatic choice for this project, but it's not something I'd do for a larger application. The next step would be splitting into proper feature modules.

## Q&A 备用答案

**Q: 为什么选择 Flutter 而不是 React Native 或原生开发？**
Flutter gives me a single codebase that runs on both iOS and Android, with excellent packages for maps and sensors. The performance is close to native because Flutter compiles to native ARM code — unlike JavaScript-bridge approaches.

**Q: AQI 数据的准确性如何？**
AQICN aggregates data from government monitoring stations. In urban areas like London, the nearest station is typically within 1–2 km. It's not hyper-local, but it's the same data used by public health agencies.

**Q: 为什么把所有代码放在一个文件里？**
For a single-developer project of this scope, it was faster to iterate without the overhead of module boundaries. In production, I would absolutely split it — the architecture is already internally structured with clear class boundaries.

**Q: 电池消耗怎么样？**
GPS and accelerometer streaming do consume battery. In testing, a 30-minute run uses roughly 8–12% battery, which is comparable to other GPS tracking apps like Strava.
